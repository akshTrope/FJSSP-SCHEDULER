The Generator is implemented so that it can generate various test cases based on different metrics, including:

* Flexibility
* Forceful bottleneck insertions
* Different processing-time distributions/natures
* Machine advantage

These generated test cases are also validated according to the constraints given in the problem statement.

Some useful metrics (not all metrics as of today) defined in `metrics.py` were used to analyse the results of algorithms on famous instances available in:

```text
benchmarks/flexible-jobshop
```

The best result found so far for these benchmark instances was compared with our result.

# Algorithms

This project proposes **CP-SAT** as the main algorithm for solving this problem. CP-SAT has a strong past record for solving job scheduling problems.

However, its main drawback is that CP-SAT can struggle with bigger test cases containing:

* Many operations
* Many jobs
* Many machines

Hence, we propose a hybrid solution consisting of:

```text
WOA (Whale Optimisation Algorithm)
        ↓
LNS (Large Neighbourhood Search)
        ↓
CP-SAT
```

The purpose of this hybrid approach is to use CP-SAT to further improve/tweak the best solution formed by WOA so far.

The results from these algorithms, including the machine assignments and timestamps, are printable and are properly validated so that no infeasible schedule can be considered as a better makespan.

## Most Important Use Case

The most important use case of the proposed hybrid algorithm is that it can find a result when CP-SAT alone is unable to find **any feasible schedule within a given timeframe**.

In some cases, the hybrid algorithm can also achieve a better makespan than a feasible solution found by CP-SAT.

## Overall Approach

We first run CP-SAT on any given instance.

### Case 1: CP-SAT finds an optimal schedule

If CP-SAT is able to return an **OPTIMAL** schedule, we return the best answer found by CP-SAT.

```text
Instance
   ↓
CP-SAT
   ↓
OPTIMAL
   ↓
Return CP-SAT result
```

### Case 2: CP-SAT finds a feasible schedule

If CP-SAT is able to find a **FEASIBLE** schedule but cannot prove optimality, we pass that result as a hint to one of the "whales" of WOA.

The hybrid algorithm then continues searching for a better solution.

```text
Instance
   ↓
CP-SAT
   ↓
FEASIBLE
   ↓
Pass CP-SAT result as a WOA whale
   ↓
WOA + LNS + CP-SAT
   ↓
Return the best valid result found
```

### Case 3: CP-SAT fails entirely

If CP-SAT fails to find any feasible schedule within the given timeframe, the hybrid algorithm is executed without a CP-SAT feasible solution as its initial hint.

```text
Instance
   ↓
CP-SAT
   ↓
No feasible solution
   ↓
WOA + LNS + CP-SAT
   ↓
Return hybrid result
```

In this case, the hybrid algorithm's answer is returned.

# Timeline / Evolution of the Approach

The original thought was to use only one algorithm that was a hybrid of:

```text
WOA + Tabu Search
```

However, using Tabu Search became more complex, and the results were significantly worse compared to using only CP-SAT, even for small instances.

For example, there was approximately **20–30% error** on simple instances such as the Kacem instances.

Hence, the idea of Tabu Search was discarded, and **CP-SAT was used as the main algorithm**.

The final approach therefore evolved towards:

```text
WOA + LNS + CP-SAT
```

with CP-SAT being used both as the initial solver and for further improvement/tweaking of the solutions generated by the metaheuristic approach.

# Analysis

The analysis is divided into two main parts.

## 1. Analysis on Benchmark Results

Our algorithm was run on all benchmark instances that were available on the internet and all instances that we were able to find (400+).

The results were stored in:



## 2. Improving WOA

https://www.mdpi.com/2075-1680/14/12/914

Used for improving WOA for better results.

Important ideas used:

1. After the job order is fixed, place the operation in the first available empty slot on the machine.
2. Use **Adaptive Inertia Weight**.

### Adaptive Inertia Weight

Adaptive inertia weight means that the influence of the previous movement of a whale is changed during the optimisation process.

In the beginning, a larger inertia can be used to encourage more exploration of the search space.

As the algorithm progresses, the inertia can be reduced so that the whales focus more on improving the solutions they have already found.

In simple words:

```text
Beginning:
Exponential decay weight — v(t)
More exploration → search different solutions

Later:
Cosine decay weight — w(t)
More exploitation → improve the best solutions

Beginning (t ≈ 0):
  w(t) ≈ w_max, v(t) ≈ w_max  →  strong pull toward both best whale AND random whales
  → broad exploration of the search space

Later (t ≈ T):
  w(t) ≈ w_min, v(t) ≈ w_min  →  weak pull overall, but v(t) got there faster
  → exploitation dominates, random exploration has already mostly faded out
```

This helps balance exploration and exploitation during the optimisation process.
